RepLab Rust API

Native server, PostgreSQL, API version /api/v1. This is a static reference, not Swagger.

Server 0.6.2 listens on all IPv4 interfaces at 0.0.0.0:8443, independent of Wi-Fi/DHCP address. Legacy API_BIND_IP is ignored. Use a stable client hostname with a matching HTTPS certificate and an explicit Host allowlist; do not disable certificate verification or expose the API publicly.

All API routes except login require Authorization: Bearer <access_token>.

Request bodies

Login: {"password":"your password"}
Password change: {"current_password":"...","new_password":"15+ characters"}
Settings: {"gym_name":"Gym Name","phone":"","address":""}
Member: {"name":"Member Name","phone":"+91 9876543210"}

Optional member fields: email, address, emergency_phone, notes, joined, is_active. Joining date defaults to today's IST date and cannot be in the future.

Directory query parameters: q (name/phone/exact member number), active (record status), limit (1–100, default 50), offset (nonnegative). Responses include items, total, limit, offset. Server 0.6.2 includes photo_base64 on each member with a saved registration photo. The image matches the profile response and is omitted for records without a photo; clients can keep initials as their fallback.

Login returns access_token, token_type, expires_at, admin. Sessions have a 90-day idle lifetime. Resume has no body and returns expires_at, admin after verifying the saved bearer key. Only key hashes are stored on the server. Sign-out revokes the current key; password changes revoke all keys.

There is one administrator, no default password, and no username/email requirement. The executable's create-admin command prompts for password and confirmation only. HTTPS port 8443 is fixed in the app and server. Server 0.6.2 requires schema 4. Run the explicit migration after a verified backup; existing credentials, certificates, memberships and receipts are preserved.

Dashboard summary

Server 0.6.1 adds active_plans (enabled, non-archived catalogue plans), collections_today_paise and collections_date. Today's INR integer-paise amount uses the exact same receipt/IST-date calculation as Reports, including membership and add-ons, and does not amortize prepaid payments. All summary fields use one read-only database snapshot. Zero means a verified empty catalogue/day, not a connection failure. Legacy revenue_today and attendance fields remain null because earned revenue and terminal attendance are not implemented.

Financial reports

GET /api/v1/reports/collections?from=2026-11-01&to=2026-11-09 returns INR integer-paise totals, highlights (today, yesterday, month-to-date, all-time), zero-filled daily collections, plans and numbered receipts. Dates are inclusive Asia/Kolkata calendar dates based on the immutable receipt received_at, not member joining/subscription dates. Omit from for all recorded history and to for today. Explicit dates must be 2000-01-01 through today, with from no later than to.

Daily history pages contain 14 days; receipt pages contain 20 payments. Use independent nonnegative daily_offset and receipt_offset (maximum 1,000,000). Each page includes items, total, limit, offset. Summaries cover the entire selected period, not only the loaded pages. Every response uses one read-only repeatable-read database snapshot. Future-dated receipts are excluded.

Totals split Cash/UPI and membership/personal-training/insurance. Plan groups use names/codes saved on receipts, including archived/renamed plans; their collections include add-ons. This is staff-confirmed money collected, not bank settlement verification, earned revenue or profit. Expenses, refunds and old payments never recorded in this database are not included. No new tables/migration are needed beyond schema 4.

Customizable plans

Settings → Manage plans edits the server catalogue. GET /api/v1/plans returns revision, plans, training_monthly_paise, insurance_monthly_paise, plus fixed UPI payee details. PUT replaces the catalogue using its last revision:

{
  "revision": 1,
  "plans": [
    {"code":"silver","name":"Silver Plan","description":"Strength & Fitness","active":true,
     "prices_paise":{"1":120000,"3":320000,"6":600000,"12":1200000}},
    {"code":"gold","name":"Gold Plan","description":"Silver + Cardio Access","active":true,
     "prices_paise":{"1":170000,"3":470000,"6":900000,"12":1800000}}
  ],
  "training_monthly_paise": 500000,
  "insurance_monthly_paise": 20000
}

Add plans with new stable codes. Existing codes cannot be removed; set active:false to archive instead. Names are unique ignoring case. Limits: 64 plans, 24 duration prices per plan, durations 1–120 months, positive integer-paise prices up to 1,000,000,000. Add-on rates may be zero. Do not include UPI fields in PUT; the recipient is not editable here.

Save increments the revision and records an audit atomically. A stale save gives 409 plan_catalog_changed; removing an identity gives 422 plan_archive_required. Reload after conflicting/uncertain saves. Price edits and archival never rewrite historical subscriptions or receipts.

Complete member enrollment

Fetch /api/v1/enrollment-options before collecting payment. It returns the current revision and active plans. Initial defaults are Silver ₹1,200/₹3,200/₹6,000/₹12,000 and Gold ₹1,700/₹4,700/₹9,000/₹18,000 for 1/3/6/12 calendar months, training ₹5,000/month and insurance ₹200/month. These are editable migration seeds; use the saved catalogue, not hardcoded totals. UPI payee: 8943521009@yescred, RepLab Fitness.

{
  "request_id": "00000000-0000-4000-8000-000000000001",
  "catalog_revision": 1,
  "member": {"name":"Test Member","phone":"+91 9876543210",
             "address":"Synthetic address","emergency_phone":"+91 9876543211"},
  "photo_base64": "<base64 JPEG/PNG profile photo>",
  "plan_code": "gold", "months": 3, "starts_on": "<today's IST YYYY-MM-DD>",
  "training_months": 1, "insurance_months": 2,
  "payment_method": "upi", "payment_reference": "optional reference",
  "payment_confirmed": true
}

POST this to /api/v1/members/enroll only after staff verifies the full amount received. With the initial defaults this example totals ₹10,100 (1,010,000 integer paise). Client totals are rejected. Required: address/emergency phone, photo, plan and explicit full-payment confirmation. Cash/UPI only; QR scanning is not bank verification. Add-ons have independent durations 0 through the plan duration and start with the plan. Start date is today through 366 days ahead. End dates are inclusive, clamped monthly anniversary minus one day.

Photos are JPEG/PNG, at most 2 MiB decoded and 1024×1024 pixels. The server strips metadata and stores a 512×512-or-smaller JPEG in PostgreSQL. The enrollment JSON limit is 3 MiB, plans 128 KiB; other routes remain limited to 16 KiB. This is a profile photo, not a biometric template or terminal enrollment. Insurance selection does not issue an insurance policy.

Member, photo/subscription, numbered append-only receipt and audit commit together. Generate a new UUID for each registration. Retry the exact same payload/ID after a timeout to get the same member/receipt, or GET /api/v1/enrollments/{request_id} to check the result. Do not collect payment again. Changed reuse of an ID gives 409 enrollment_conflict; missing lookup gives 404 enrollment_not_found. Full profiles contain enrollment and JPEG photo_base64 when registered; old member records do not invent plans/payments.

New registrations must include catalog_revision. Missing revision gives 409 app_update_required, stale revision 409 plan_catalog_changed, archived/unavailable plan 409 plan_unavailable. These failures do not create records. Reload plans and reconcile any already collected payment before confirming again. Exact retries of completed registrations still return their original receipt after plan changes, including legacy requests.

Error format: {"error":{"code":"...","message":"..."}}. Request IDs are in X-Request-ID. Login rate-limit responses include Retry-After.

Attendance, renewals/refunds, billing reports and terminal integration are not available yet. Unavailable dashboard totals are null, not invented zeros. An active member record does not establish entry rights.
